# コミットメッセージ書き（commit-note）

> **これは「スキル鍛冶」に同梱された見本です（Claude Code専用形の書き方見本）。** そのまま使えますし、自分用に書き換えてもかまいません。

一人で開発している人の、その日の変更のコミットメッセージ書きを引き受けるスキル。
「修正」「更新」「いろいろ」だけが並んだ履歴から卒業して、半年後の自分が読んで分かるログにするのが目的です。

**むいている場面**：作業がひと区切りついて、これからコミットするとき。1日の終わりのまとめコミット。
**むいていない場面**：まだ動作確認が済んでいない変更（先に確認してください）。何百ファイルにも及ぶ大規模な一括変更（分割してから呼んでください）。

> **このスキルはClaude Code向けに書いてあります。**
> AIが自分でgitのコマンドを動かして、変更の中身を実際に読むことを前提にしています。
> コマンドを動かせないAIで使うと、手順1から先に進めません。

## 進め方

### 1. 今どうなっているかを見る

`git status` を実行して、次の3つを把握する（理由：ステージ済みだけを書くのか、未ステージまで含めるのかで、書くべき文面が変わるため）。

確認すること：
- ステージ済み（コミット予定）の変更があるか
- 未ステージの変更があるか
- 追跡されていない新規ファイルがあるか

### 2. 変更の中身を実際に読む

`git diff --staged` を実行して、ステージ済みの中身を読む。ステージ済みが何も無ければ `git diff` を実行して未ステージの中身を読む（理由：差分を読まずにファイル名だけで書いたメッセージは、たいてい実際の変更とずれるため）。

差分が長くて読み切れないときは、`git diff --staged --stat` でファイルごとの増減を先に見て、変更量の多いファイルから読む。

### 3. 直近の履歴に書き方を合わせる

`git log --oneline -10` を実行して、このリポジトリでこれまでどう書かれてきたかを見る（理由：1本だけ書き方の違うメッセージが混ざると、履歴が読みにくくなるため）。

見るところ：日本語か英語か、`feat:` のような接頭辞を使っているか、1行目の長さ、句点を打つか。

### 4. 変更を「なぜ」でまとめる

読んだ差分を、**目的ごとに**まとめる（理由：ファイル単位で並べると「AとBとCを変更」という、差分を見れば分かることの繰り返しになるため。知りたいのは、なぜ触ったのかです）。

1つのコミットに目的が2つ以上またがっていたら、分割を提案する。

**「なぜ」は、差分から読み取れる範囲だけを書く。** 差分に現れていない理由（どんな不具合が起きていたか、誰から言われたか、どの環境で困っていたか）は、**推測で書かず `〈なぜ：要確認〉` と空けて、本人に1回聞く**（理由：もっともらしい理由を補うと、それが履歴に残って事実として引き継がれます。半年後にその嘘を読むのは自分です）。

- 差分から読み取れること：何が変わったか、どう変わったか、どこに影響するか
- 差分から読み取れないこと：**なぜ変えようと思ったか**（きっかけ・症状・依頼元）

### 5. メッセージを組み立てて見せる

下の「出力の型」に沿って書き、**画面に出して本人に見せる**。

### 6. コミットは本人の合図を待つ

メッセージを見せたら、そこで止まる。「これでコミットして」と言われてから `git commit` を実行する（理由：コミットの取り消しは面倒なため）。

**pushは、AIからは実行しない。** 利用者が「pushして」と**明示的に頼んだときだけ**、実行する前に**何を・どこへ送るのかを要約して確認を取る**（例：「〈ブランチ名〉に〈n〉件のコミットを〈送り先〉へ送ります。よろしいですか」）（理由：pushは他人の環境にも届く、取り消しの難しい操作だからです。コミットまでは手元の話ですが、pushから先は外に出る話になります）。

## 判断ルール（分かれ道）

| 場面 | どうするか | 理由 |
|---|---|---|
| ステージ済みが何も無い | 未ステージの変更を読んで書き、「まだ何もステージされていません」と添える | 勝手に `git add` すると、本人が意図的に外していた変更まで巻き込む |
| 変更が2つ以上の目的にまたがる | 目的ごとにメッセージ案を分けて出し、分割を提案する（書き方は「出力の型」の**分割案のとき**を使う） | 1つのコミットに混ぜると、あとで片方だけ戻すことができなくなる |
| **直近のログが英語で書かれている** | 日本語案と英語案を**両方**出して、どちらでそろえるか聞く | 履歴の言語をそろえるかどうかは、そのリポジトリを誰が読むかで決まる話で、AIが決めることではない |
| **追跡されていない新規ファイルがある** | メッセージには含めず、「〈ファイル名〉はまだ追跡されていません。含めますか」と1行添える | 書きかけのメモや個人的な下書きが紛れていることが多く、勝手に含めると外せなくなる |
| 変更が自動生成ファイルだけ（ロックファイル等） | 1行目だけの短いメッセージにする | 生成物に「なぜ」は無いので、本文を書くと水増しになる |
| 差分の中にパスワード・APIキーらしき文字列がある | **メッセージを書く前に手を止めて本人に知らせる** | コミットしてしまうと、あとから消しても履歴に残る |

## 出力の型

**ふつうのとき（目的が1つ）**

```
【コミットメッセージ案】

〈1行目：何をしたかの要約。日本語で50字以内。句点は打たない〉

〈本文：なぜそうしたか。1行を80字くらいで折り返す。箇条書きでもよい〉

---
対象ファイル：〈n〉件（〈主なファイル名〉ほか）
ステージ状況：〈ステージ済みのみ／未ステージを含む〉
```

**分割案のとき（目的が2つ以上）**

```
【この変更は、目的が〈n〉つに分かれています。分けてコミットすることをおすすめします】

■ 案1：〈目的の名前〉
対象：〈ファイル名〉
　〈1行目〉

　〈本文〉

■ 案2：〈目的の名前〉
対象：〈ファイル名〉
　〈1行目〉

　〈本文〉

――――――
分けずに1つにまとめる場合の案：
　〈1行目〉
```

**分けたあとの操作は本人が行います。** AIは案を出すところまでです（理由：どのファイルをどちらに寄せるかは、本人の意図が要るためです）。

## 合格ライン（これを満たしたら完成）

- [ ] 1行目だけ読んで、何をしたコミットか分かる（日本語で50字以内）
- [ ] 本文に「なぜそうしたか」が書いてある（差分を見れば分かることの繰り返しになっていない）
- [ ] **本文の「なぜ」が、差分から確認できる範囲で書かれている（推測で理由を補っていない）**
- [ ] 直近10件のログと、言語・接頭辞・句点の有無がそろっている（英語ログのときは両案を出している）
- [ ] `〈 〉` の穴（未確定の箇所）が1つも残っていない＝そのままコピーして使える状態になっている
      ※ `〈なぜ：要確認〉` は、本人に聞くために意図して残す印なので穴には数えません

## やってはいけないこと

- **差分を読まずに、ファイル名だけで書かない。** 「テストを修正」と書いたら中身は設定変更だった、が実際に起きます
- **`git add -A` で全部まとめてステージしない。** 本人が意図的に外している変更があります
- **頼まれていないのにコミットしない。** 合図を待ちます
- **pushはAIから実行しない。** 明示的に頼まれたときだけ、内容を要約して確認を取ってから送ります
- **「various fixes」「いろいろ修正」で済ませない。** それは何も書いていないのと同じです
- **差分に無い理由を、それらしく書かない。** 「〜で不具合が出ていたため」は、差分からは分かりません。分からないものは `〈なぜ：要確認〉` と空けて聞きます
