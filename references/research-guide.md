# 調べて超える（工程③・④の手引き）

工程③に入ったら、このファイルを開いてから動く。

## なぜ調べるのか

**市場の類似より劣るスキルは、配っても売っても選ばれません。** そして自分で使うだけの場合でも、すでに良いものがあるならそれを使ったほうが得です。

だから作る前に必ず見にいきます。目的は3つ。

1. **すでに十分良いものがあるか**を知る（あるなら、作らずに済むかもしれない）
2. **あるなら、その弱点はどこか**を知る（そこが、こちらの勝ち筋になる）
3. **どこで超えるか**を、作り始める前に言葉にする

調べずに作ったスキルは、たいてい「もうあるものの劣化版」になります。順番が品質を決めます。

## この工程のゴール（成果物は比較表1枚）

下の表が埋まるまでが工程③です。**表が無い状態で工程④（超え方の設計）に進むのは禁止**です。

| # | 名前 | どこにあるか | 普及の手がかり（スター数／掲載順位／無ければ不明） | 最終更新 | 機能の範囲 | 弱点（＝こちらの狙い目） |
|---|---|---|---|---|---|---|
| 1 | | | | | | |
| 2 | | | | | | |
| 3 | | | | | | |

**まず、実際に1回検索を実行する。** 「検索できないかもしれない」と自己申告で飛ばさない。実行してエラーになった場合だけ、後述の**質問版**に切り替える（理由：やってみれば動くことが多く、やらずに諦めると調査工程そのものが形だけになるため）。

**埋め方の目安**

- 見つからなかったら、**「◯年◯月◯日時点で、この探し方では見つけられませんでした」**と日付つきで書く。「存在しない」「世界初」とは書かない（理由：探し方の外にある可能性を消せないため。断定は、あとで1件見つかった瞬間に信用を失います）
- 最終更新日が画面から取れないときは「取得できず（更新の活発さで代替：直近のコミットや告知の日付）」と書く
- **土俵の違う類似**（目的は同じだが形が別。例：スキルでなく有料記事・アプリ）は、比較表に「参考（土俵違い）」として1行だけ載せてよい。主戦の比較対象には数えない
- 3件も見つからないときは、探し方（キーワード）を変えてもう一度。日本語・英語の両方で試す
- 5件を超えたら、上位3件に絞る（全部並べても判断が鈍るだけ）
- **比較の主対象は、無料で中身が読めるもの**にする。有料で売られているものは中身を確認できないので、弱点欄に **「中身未確認（販売ページの記載範囲のみ）」** と書いてよい（理由：読んでいないものの弱点を書くと、それは推測であって調査ではなくなるためです）
- 普及の手がかりが分からないときは、空欄にせず **「不明」** と書く（販売ページや紹介ページには、スター数のような数字が無いことが普通です）

## どこを見るか（3か所）

### 1. GitHub（世界の作り手が置いている場所）

GitHub は、世界中の作り手が自分の作ったものを置いている**巨大な公開棚**だと思ってください。無料で誰でも見られます。

**探し方**

- 検索窓に、作ろうとしているものの言葉を入れる。**日本語と英語の両方**で（例：「請求書 スキル」「invoice skill」「claude skill invoice」）
- 「Agent Skills」「claude skills」「awesome claude」のような、スキルを集めた一覧ページも探す。1つ見つかると、そこから何十件もたどれます

**見るべき数字は3つ**

| 見るところ | 何が分かるか |
|---|---|
| **スター（☆）の数** | どれくらいの人が「これいい」と印をつけたか。**普及度の目安**。数十なら小さい、数千なら定番 |
| **最終更新日**（Updated ◯日前） | 生きているか死んでいるか。**1年以上動いていないものは、すでに現実とズレている可能性が高い**＝そこが弱点 |
| **README（説明書）の中身** | 何ができて、何ができないか。ここに書いていないことが、その作品の守備範囲の外 |

### 2. スキルのマーケット（公式・コミュニティのカタログ）

スキルやプラグインをまとめて紹介している場所を見る。**同じ名前・同じ目的のものが並んでいたら、その分野はすでに埋まっています。**

見るときは、いちばん上に出てくるものだけでなく、**2番手・3番手の説明文**まで読む。1番手が押さえていない部分が、たいてい書いてあります。

### 3. 販売されている場所（有料の同種品があるか）

note や Brain のような**個人が有料の資料やノウハウを売っている場所**でも、同じ目的のスキル・手順書が売られていないかを見ます。

見るのは**どんな中身がウリになっているか**だけです。値段の話はしません（このスキルは値付けの指南をしません。値段はあなたの仕事の価値であって、AIが決めることではないからです）。

## 弱点の見つけ方（狙い目のパターン）

類似品を見つけたら、次の観点で弱点を探します。ほとんどの場合、どれかに当てはまります。

| 観点 | 弱点になっているサイン | こちらの超え方の例 |
|---|---|---|
| **言語** | 英語だけ。日本語の説明が無い | 日本語で、会話しながら進める |
| **前提知識** | 用語の説明が無く、エンジニア向けに書かれている | 用語をその場で言い換える。ターミナル前提にしない |
| **聞き取り** | いきなり作り始める。使う人の事情を聞かない | 提案式で聞き切ってから作る |
| **完成後** | 作って終わり。動くかどうかは使う人まかせ | 実走検証して、不具合と改修プランまで出す |
| **鮮度** | 1年以上更新が止まっている | 現在の仕様に合わせる（ただし時点を明記する） |
| **範囲** | 一部の工程しか面倒を見ない | 前後の工程までつなげる |
| **説明書** | READMEが数行しかない／使い方の例が無い | 最初の一言・具体例・つまずいたときの直し方まで書く |
| **記録** | 使っても何も残らない | 作品ノートのような蓄積の仕組みを持たせる |

**弱点が1つも見つからないこともあります。** そのときは正直にそう言うこと（次節）。

## 工程④：超え方の設計（比較表が埋まってから）

比較表を利用者に見せて、次の1枚を作り、合意を取ります。

```
■ スキル名（案）：
■ 一行定義（誰の・何を・どう楽にするか）：
■ 起動の合図（description案）：
■ 手順の骨子：
■ 出力の型：
■ 参照ファイルを分けるか：

■ 超え方（ここが本体）
  類似①「〈名前〉」の弱点〈…〉 → この設計の〈どこ〉で潰す
  類似②「〈名前〉」の弱点〈…〉 → この設計の〈どこ〉で潰す
```

**「超え方」の欄が埋まらないなら、まだ作ってはいけません。** 埋まらないということは、既存品との違いが自分でも説明できないということで、それは使う人にも説明できないということです。

### 作らない勇気

類似が十分に強くて超えられないと判断したら、**正直にそう伝える**。伝え方の例：

> 調べたところ、〈名前〉というスキルがすでにあって、〈できること〉まで面倒を見ています。更新も続いていて、日本語の説明もあります。今のままの企画だと、これより良いものにはならないと思います。
> 代わりに、切り口を変える案を3つ出します。①対象を〈もっと狭い相手〉に絞る ②〈前後のこの工程〉までつなげる ③〈この業種〉のやり方に特化する — どれか、ひっかかるものはありますか。

そのうえで**工程①に戻ります**。やめたアイデアは、作品ノートの「供養欄」に**作らなかった理由まで**書いて残す（理由：判断の記録があると、半年後に同じ調査をやり直さずに済むため）。

## 検索できる環境が無い場合（質問版）

**このルートに入ってよいのは、実際に1回検索を試してエラーになったときだけです。** 試さずに切り替えない。

インターネット検索が使えない環境でも、**この工程は飛ばしません。** 精度は落ちますが、代わりの手順があります。

### 手順

1. **AIが知っている範囲で候補を挙げる**：「同じ目的のものとしては、こういう種類のものが一般的にあります」と3つ程度、種類として挙げる
2. **必ず前置きを付ける**：「これは検索して確かめたものではなく、**私の知っている範囲の一般論**です。実際の最新状況とは違う可能性があります」（理由：確認していないものを確認済みのように出すのが、一番信用を失う行為だから）
3. **利用者に確認してもらう場所を渡す**：「お手すきのときに、GitHubで『〈英語のキーワード〉』と検索して、上位3件だけ見てもらえますか。スターの数と最終更新日をメモしてくださると、比較表が埋まります」
4. **比較表には「未確認」と明記する**：空欄のままにせず、`未確認（◯年◯月◯日時点・検索環境なし）` と書く
5. 利用者が「そこまではいい」と言ったら、**未確認のまま進めることに合意した記録を残して**進む。人に配る予定がある場合だけは、**配る前に必ず確認してもらう**（理由：自分用なら被っても損はないが、配るなら被りは信用問題になるため）

### 質問版で聞くこと

> 今この環境ではインターネット検索ができないので、代わりに教えてください。
> - 同じ目的のツールやスキルで、**すでに知っているもの・使ってみたもの**はありますか
> - それを使ってみて、**物足りなかったところ**はどこでしたか
> - もし無いなら、今その作業で**一番手間なのはどの部分**ですか

**使ってみて物足りなかったところ**が、そのまま最強の弱点情報になります。検索より正確なことすらあります。

### 質問版ルートでの「超え方」の埋め方（工程④）

比較表が「未確認」だらけになるので、工程④の**超え方の欄は「利用者が実際に不便だった点」で埋めます。**

```
■ 超え方（質問版ルート）
  利用者が不便だった点：〈聞き取った内容をそのまま〉
   → この設計の〈どこ〉で解消する
```

これは「既存品の弱点を突いた」証明にはなりませんが、**目の前の一人の不便は確実に実在する**ので、設計の根拠として十分に成立します。人に配る前には、改めて工程③の検索版をやり直してください。

## 書き方のルール（調査結果を文章にするとき）

- **日付を必ず添える。** 「◯年◯月◯日時点で調べた範囲では」の一言を落とさない
- **「世界初」「唯一」「日本語では存在しない」と書かない。** 探し方の外は見えていません。書くなら「この探し方では見つけられませんでした」
- **確認したことと、知っているつもりのことを混ぜない。** 検索して見たものと、AIの知識から言っているものは、必ず分けて書く
- **競合の弱点は、一次情報の原文で裏を取る。** 機能の一部にしか当たらない制約を、その競合全体の前提として書かない（弱点を過大に書くと、そこに乗せた「超え方」ごと崩れます）
- **調査結果は3か月をめどに見直す。** ソフトの世界は動きが速く、半年前の「弱点」はもう直っていることがあります
