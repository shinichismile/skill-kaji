# 第1部　鍛える（工程⑥）

## 1. AIの自走検証ループ（AIが自分で回す）

書き上げたスキルを、**AI自身がその場で使ってみます。** 読み返すだけでは手順の穴は見つかりません。動かすと必ず露出します。

合格するまで (a)→(b)→(c)→(d)→(a) を回します。

### (a) 実走テスト

**試しの依頼を1件用意して、作ったスキルの手順どおりに、AI自身が最後まで実行してみる。**

試しの依頼は、利用者に出してもらうのが一番です（「いつもの仕事で、直近にやった1件を題材にください」）。もらえない場合は、AIが**それらしい仮の1件**を作って「この題材でやってみます」と断ってから進める。

実行しながら、次の3つを記録する。

| 記録すること | 例 |
|---|---|
| **詰まった箇所** | 「手順3の『いつもの体裁で』が、何を指すのか分からなかった」 |
| **勝手に補った箇所** | 「宛名の敬称が書いていなかったので『様』にした」 |
| **順番が回らなかった箇所** | 「手順2で必要な情報が、手順4でしか出てこない」 |

**勝手に補った箇所は、全部が不具合です。** 補えたのは今回たまたまで、次は違う補い方をします。

### (b) 点検

出来上がったものを、**工程①で決めた合格ラインと1項目ずつ**突き合わせる。感想（「良さそうです」）は書かない。項目ごとに○×をつける。

**合格ラインには、利用者が挙げた項目に加えて、必ずこの1項目を足す**：「`〈 〉` の穴（未確定の箇所）が1つも残っていない＝そのまま使える状態になっている」（理由：穴あきの出力は、どれだけ型が良くても完成品ではないため）。

**合格ラインの文言は、検証ループの途中で変更・緩和してはいけない。** どうしても変えたい場合は「基準変更」として利用者に見せ、承認を取ってから（理由：基準を緩めてループを抜けると、検品が形だけになるため）。

```
合格ライン照合
[○] 決まった項目が5つとも埋まっている
[×] いつもの言い回しになっている → 「弊社」を使ったが、見本では「当方」だった
[○] 3分で読める長さ（推定1分40秒）
```

### (c) 不具合レポート（利用者に見せる。隠さない）

見つかった問題を**件数と中身つきで一覧にして**、利用者に報告する。

```
実走してみた結果、3件の不具合が出ました。

1. 手順3の「いつもの体裁で」が具体的でなく、私の判断で決めてしまいました
2. 敬称の指定がなく、勝手に「様」にしました
3. 「当方」と書くべきところを「弊社」と書きました（見本と食い違い）
```

**黙って直してはいけません。** 黙って直すと、利用者は自分のスキルの弱点を知らないまま使い続けることになります。報告することで、利用者自身が「あ、そこは自分でも曖昧だった」と気づけます。

### (d) 改修プラン

**どこを・どう直すか**の具体案を出す。抽象的な方針（「もっと明確にします」）ではなく、**書き換える文そのもの**を見せる。

```
直し方の案です。よろしければこの内容で書き換えます。

1. 手順3 →「見本ファイルの体裁に合わせる（項目の順番・見出しの大きさ・余白）」に書き換え
2. 「判断ルール」に1行追加 →「宛名の敬称は、法人なら『御中』、個人なら『様』」
3. 「やってはいけないこと」に1行追加 →「自社を『弊社』と書かない。見本どおり『当方』」
```

利用者のOKをもらって直したら、**(a)に戻る。** 合格ラインが全項目○になるまで繰り返す。

**3周回っても合格しない場合**は、いったん止めて利用者に相談する（理由：3周で直らないのは、書き方の問題ではなく、そもそもの手順設計や合格ラインが定まっていない可能性が高いため。工程①に戻ったほうが速い）。

## 2. 検品（自走ループを抜けてから）

### 2-1. 机上の発動テスト（AIがやる）

利用者が言いそうな頼み方を**10通り**書き出し、description と1つずつ突き合わせて○×をつける。

```
| # | 言いそうな頼み方 | 発動するか | 根拠 |
|---|---|---|---|
| 1 | 週報書いて | ○ | descriptionに同じ言い方あり |
| 2 | 今週のまとめお願い | △ | 「まとめ」は入っていない → 追加を提案 |
| 3 | 報告書作って | ○ | 「報告」で拾える |
...
```

**○が8つ未満なら、description に言い方を足して数え直す。** 10通りのうち8つ以上が○になれば合格です（理由：発動しないスキルは、存在しないのと同じだから）。

**あわせて、発動してはいけない言い方も3つ試す。** 作るスキルと無関係の依頼（例：返信スキルに対して「借りた本返しといて」）を3つ書き出し、**×が付くこと**を確かめる（理由：何にでも当たる言い方をdescriptionに入れると点数は上がりますが、誤発動を量産します。当たりすぎるスキルは、外れるスキルと同じくらい邪魔です）。

10通りは、**わざと言い方をばらけさせる**こと。丁寧な言い方・雑な言い方・略した言い方・別の呼び名を混ぜる。

### 2-2. 実際の発動テスト（利用者がやる。AIは代行できない）

利用者に依頼する。

> **新しいチャットを開いて**、「〇〇して」と話しかけてみてください。作った直後の同じ会話では、まだ読み込まれていないので反応しないことがあります。故障ではありません。
> （この仕事のフォルダ専用で保存した場合は、**そのフォルダを開いた状態で新しいチャットを始めてください**）
>
> **発動したかどうかの見分け方**：返事の中に「〈スキル名〉を使います」と出るか、出力が「出力の型」どおりの形になっていれば発動しています。分からなければ、そのチャットで「いま何のスキルを使いましたか」と聞いてください。
>
> 反応しないときは、まずアプリを閉じて開き直し、もう一度新しいチャットで試してください。それでも反応しなければ、実際に打った言葉をそのまま教えてください。
>
> うまくいったら、そのときの**やりとりをそのままコピーして**貼ってください。検品の記録に残します。

**AIが「発動しました」と報告してはいけません。** 確認できるのは利用者の画面だけです。

### 2-3. 先に失敗を観測する

**スキル無しで同じ依頼をしたら、AIがどう間違うか**を先に見ます。

やり方：スキルを使わない状態で同じ題材をやってみて、出てきた間違いを列挙する。そのうえで、その間違いを塞ぐ形でスキルを書き直す。

理由：想像で書いた注意書き（「丁寧に書くこと」）より、実際に起きた失敗を潰した注意書き（「箇条書きだけで終わらせない。必ず冒頭に3行の要約をつける」）のほうが、圧倒的に効きます。

### 2-4. 混入チェック（人に渡す予定があるなら必須）

**自分用のつもりで書いたものには、ほぼ必ず個人的な情報が混ざります。** 記憶に頼らず、決まった言葉で機械的に探します。

**フォルダの中の全ファイル**（SKILL.md、references/、見本ファイルすべて）を対象に、次の言葉を1つずつ検索する。

リストは2段になっています。**上の5つは全員必ずやります。** 下は、コードや設定を書き込んだ人だけで大丈夫です。

#### 【全員必ずやる5つ】

| # | 探すもの | 検索する言葉 | 見つかったときの見方 |
|---|---|---|---|
| 1 | メール・SNSのID | `@` | メールアドレスとSNSのIDが一度に見つかります |
| 2 | **人名（いちばん見落とす）** | `様` / `さま` / `御中` / `専用` / `オーダー` / `受注` | **これらの直前にある語は人名・社名の疑いあり。必ず1件ずつ利用者に確認する**（例：「田中様」「〈…〉様専用」） |
| 3 | 住所 | `県` / `市` / `区` / `町` / `丁目` / `〒`（**1字だけで検索する**） | 1字検索なので取りこぼしません。そのぶん誤検出も出ます |
| 4 | 電話・郵便番号・口座 | **4桁以上の数字の並びを目で追う** | 検索語では拾いきれないので、ここだけは目視で確認します |
| 5 | 自分の氏名・屋号 | **利用者に列挙してもらう**（本名・ふりがな・屋号・会社名・お客様の名前） | 何が個人情報かは本人にしか分かりません。必ず口頭で挙げてもらう |

#### 【コードや設定を書いた人だけ】

`api` / `API_KEY` / `token` / `secret` / `Bearer` / `sk-` / `password` / `パスワード` / `認証` / `localhost` / `\Users\`（Windowsの絶対パス） / `/Users/` / `/home/`（Mac・Linuxの絶対パス）

#### 誤検出の注意

**1字検索や短い語は、関係ない言葉にも当たります。** 例えば `パス` は「パスタ」「パスワード変更の説明文」にも当たり、`市` は「市販」「都市」にも当たります。**ヒットしたら必ず前後を読んで判定してください。** 件数だけ見て「多いから危ない」と判断しないこと。

**判定のしかた**

- 見つかったら、**1件ずつ利用者に見せて**「これは残しますか、置き換えますか」と聞く（勝手に消さない。必要な記述のこともあるため）
- 置き換えるときは `〈会社名〉` `〈あなたの名前〉` のような**穴埋めの形**にする（消すだけだと、使う人が何を入れればいいか分からなくなります）
- **絶対パスは、必ず穴埋めか相対的な書き方に直す。** あなたのパソコンにしかないフォルダの道順は、他人の環境では100%動きません

**もう1つの確認：「あなたの環境で実行できますか」テスト**

手順の文を**1文ずつ**読んで、「これは、このスキルを受け取った人の環境でそのまま実行できるか？」を判定する。できないもの（自分だけが持っているファイル・自分だけが入れているツール・自分だけが知っている社内ルールに依存する文）は、書き換えるか、前提として明記する。

### 2-5. 証跡義務（これが検品の背骨）

**やったテストは、生の入力と出力をそのまま検品ログに貼ります。** 「テストしました・問題ありませんでした」という報告は、証跡がなければ**無効**として扱います。

**貼れないものは不合格（FAIL）です。** 理由：貼れないということは、実際にはやっていないか、結果が見せられない状態だということだからです。

**検品ログの型**（`検品ログ.md` としてスキルのフォルダの外に保存する。人に配るときは同梱しない）

```markdown
# 検品ログ：〈スキル名〉
検品日：〈YYYY-MM-DD〉

## 1. 自走検証ループ
- 周回数：〈n〉周
- 最終の合格ライン照合：
  [○] 〈項目〉
  [○] 〈項目〉
- 出た不具合と直した内容：
  1. 〈不具合〉 → 〈直した内容〉

### 実走テストの生記録（1周目）　※周回ごとに、この欄をそのまま繰り返して貼る
**入力（試しの依頼）**
〈実際に打った依頼文をそのまま〉

**出力（できあがったもの）**
〈実際に出てきたものをそのまま〉

### 実走テストの生記録（2周目）
**入力（試しの依頼）**
〈…〉
**出力（できあがったもの）**
〈…〉

## 2. 机上の発動テスト
| # | 言い方 | 判定 | 根拠 |
|---|---|---|---|
| 1 | 〈…〉 | ○ | 〈…〉 |
（10行）
結果：○〈n〉／10

## 3. 実際の発動テスト（利用者が実施）
実施状況：[ ] 実施済み ／ [ ] 未実施
**利用者が打った言葉**
〈そのまま〉
**返ってきた反応**
〈そのまま貼る〉

## 4. 混入チェック
| 分類 | 検索語 | ヒット件数 | 処理 |
|---|---|---|---|
| メール・SNS | `@` | 〈n〉 | 〈残した／置き換えた〉 |
| 人名 | `様`・`さま`・`御中`・`専用`・`オーダー`・`受注` | 〈n〉 | 〈…〉 |
| 住所 | `県`・`市`・`区`・`町`・`丁目`・`〒` | 〈n〉 | 〈…〉 |
| 数字の並び（目視） | 4桁以上 | 〈n〉 | 〈…〉 |
| 氏名・屋号 | 〈利用者が挙げた語〉 | 〈n〉 | 〈…〉 |
| （該当者のみ）鍵・パス | `api`ほか | 〈n〉 | 〈…〉 |

## 5. 判定
- [ ] PASS / [ ] FAIL
- 根拠（1行）：〈なぜその判定か〉
```

**PASS / FAIL には必ず根拠を1行つける。** 「問題なし」は根拠ではありません。「合格ライン5項目すべて○、発動テスト9/10、混入0件のためPASS」のように、数字で書きます。

### 2-6. 停止規定（工程⑥の）

- **FAILが1つでも残っているうちは、工程⑦に進まない・梱包しない。** 「あとで直します」で先へ進めない（理由：配ってからの回収はできないため）
- **証跡が貼れないテストは、実施していないものとして扱う**
- **利用者が実際の発動テストをやらない場合は「未実施」と書き、FAILのまま据え置く。梱包しない**（理由：発動しないスキルは、受け取った人の手元では存在しないのと同じだからです。自分用に使い続けるぶんには構いませんが、人に渡す資格はまだありません）

# 第2部　世に出す（工程⑦・任意）

出口は2つだけです。

## (a) 自分用のまま使う

**これで完全に完結します。** 何も足す必要はありません。作品ノートに1行書いて終わりです。

配ることを勧めもしません。自分の仕事が楽になったなら、それが目的の達成です。

## (b) 梱包して渡す・売る

**前提：検品でPASSが出ていること。混入チェックが済んでいること。** 落ちたものは梱包しません。

### 手順（非エンジニア向け）

**1. 配る用のフォルダを作る**

スキルのフォルダを**まるごとコピー**して、配布用の場所に置く。中身は次のとおり。

```
〈スキル名〉/
├── SKILL.md          ← 本体
├── references/       ← 使うなら（無ければ不要）
├── README.md         ← 説明書（下記）
└── LICENSE.md        ← 利用条件（下記）
```

**入れてはいけないもの**：検品ログ、作品ノート、あなたの実物の見本（顧客名などが入っているもの）。

**2. README.md（説明書）を作る**

受け取った人が最初に開くファイルです。長く書く必要はありません。**次の4つだけ**。

```markdown
# 〈スキル名〉

〈何ができるか、3行で〉

## 入れ方
1. このフォルダを、〈保存先〉に置いてください
2. AIのアプリを一度閉じて、開き直してください

## 最初の一言
新しいチャットで「〈頼み方の例〉」と話しかけてください。

## 利用条件
LICENSE.md をご覧ください。
```

**「最初の一言」を必ず書く。** これが無いと、受け取った人は「入れたけど、どう使うんだ？」で止まります。**配布物でいちばん多い失敗がこれです。**

**3. LICENSE.md（利用条件）を入れる — 本人に聞いてから組む**

「使っていい範囲」を書いた紙です。無いと、受け取った人は改造していいのか・仕事に使っていいのか分からず、結局使いません。

**⚠️この表からAIが選んではいけません。** 先に、このファイルの後半にある**「利用条件は、本人に聞いて決める」の3問＋1問**を本人に聞き、その答えで決めます（停止規定⑥）。下の表は、**答えを条件文に変換するための早見**です。

**大事な注意：スキル鍛冶自体が「全部自由」なのは、この作品の作者がそう決めただけで、あなたの作品の正解ではありません。** 特に売る場合、「全部自由」の文を写すと**買った人が無料で配れてしまい、商品として成立しません。** 配り方に合わせて選んでください。

| 配り方 | 合う条件 | 文例（そのまま使えます） |
|---|---|---|
| **無料で広く配る**（たくさんの人に届いてほしい） | 自由型 | 「無料で使えます。改造・再配布も自由です」（スキル鍛冶のLICENSE.mdを雛形にしてOK） |
| **無料だが、配るのは自分の窓口から**（誰に届いたか把握したい） | 共有型 | 「利用・改造は自由です。再配布はせず、欲しい方にはこの配布ページを案内してください」 |
| **売る** | **販売型** | 「購入者ご本人の利用に限ります。ファイルの再配布・転売・第三者との共有はできません。ご自身の仕事に使うこと・自分用に改造することは自由です」 |
| 迷っている | まず共有型 | あとから自由型に広げるのは簡単ですが、逆（自由→制限）はできません（すでに配った分は回収できないため） |

売る場合は、**販売するプラットフォームの規約**（返金・表記のルール等）も出品前に一度確認してください。

**4. zip（圧縮ファイル）にまとめる**

zipは、**複数のファイルを1つの箱に詰めて持ち運べるようにしたもの**です。相手はそれを開く（解凍する）だけで、中身が元どおりの形で出てきます。

- **Windows**：フォルダを右クリック →「圧縮」または「ZIPファイルに圧縮する」
- **Mac**：フォルダを右クリック（またはControlを押しながらクリック）→「"〈名前〉"を圧縮」

できた `.zip` ファイルが、そのまま配る物です。

**5. 渡す**

手渡し、メール添付、ファイル共有サービス、販売プラットフォームなど、方法は自由です。

> **停止規定：配布・販売・アップロード・公開の最後のボタンは、必ずあなたが押してください。**
> AIがやるのは、渡せる状態のzipを用意するところまでです。送信や公開の操作をAIに代行させないでください（理由：一度外に出たものは回収できないため）。

### 売ることについて

このスキルで作った作品は**完全にあなたのもの**です。無料で配るのも、有料で売るのも自由です（`LICENSE.md` 参照）。

ただし、**いくらで売るかの相談には乗りません。** 値段はあなたの仕事の価値であって、AIが決めることではないからです。

### 利用条件は、本人に聞いて決める（AIが必ず聞く）

作品を他の人がどう扱ってよいかを決められるのは、**作った本人だけ**です。AIが勝手にライセンスを付けてはいけません。梱包の前に、AIは**必ずこの3つを本人に聞く**：

> あなたのこのスキル、受け取った人が——
> 1. **自分用にカスタマイズ（改造）するのは**、OKですか？
> 2. **そのまま、または改造した版を、ほかの人に配るのは**、OKですか？
> 3. **販売するのは**、OKですか？
>
> あわせて、**どう配りますか**——zipを手渡し／GitHubで公開／販売ページに置く、など。

**答えから利用条件を組み立てる早見**：

- 1〜3ぜんぶOK → **自由型**（上の表の文例）
- 1・2はOK、3はダメ → 自由型の文＋「販売はご遠慮ください」の1行
- 1だけOK → **共有型**寄り（「利用・改造は自由。再配布はこの配布ページの案内で」）
- 売り物にする → **販売型**（購入者本人のみ・再配布/転売禁止）

答えをそのままLICENSE.mdの文に落とし、**本人に読み上げて確認を取ってから**梱包します。
